# 框架对比：手写循环与 LangGraph

2026-11-27 · 原始记录 `experiments/framework_comparison.json` · 重跑 `.venv/bin/python -m tiny_agent.compare_frameworks`

同一个 Agent 写了两遍：`tiny_agent/agent.py`（手写循环）和 `tiny_agent/graph_agent.py`（LangGraph 1.2.20）。
两者共用模型、提示词、协议解析和工具，只有“谁来组织流程”不同。

## 测量结果

| 项目 | 手写循环 | LangGraph |
| --- | ---: | ---: |
| 代码行数 | 38 | 87 |
| 额外安装的包（含间接依赖） | 0 | 38 |
| 导入耗时 | 0.008 秒 | 0.29 秒 |
| 编排一次两步运行的耗时（模型换成立刻返回的假函数） | 0.011 毫秒 | 1.16 毫秒 |

**行为完全相同。** 32 道题、三个模型（微调 Qwen3、未微调 Qwen3、未微调 Qwen2.5），共 96 次运行，
两种写法的完整轨迹逐字一致。这些运行覆盖了正常调用（59 次）、格式错误后重试（7 次）和步数用完（2 次）三条分支。

编排开销相差约 100 倍，但两边都远小于模型生成一个 token 的时间（几毫秒到十几毫秒），在这个任务里可以忽略。

## 框架替你做了什么

1. **把循环变成一张图。** 手写版的 `for` 循环，在 LangGraph 里是两个节点（模型、工具）加两条条件边。流程画得出来，分支写在一处。
2. **合并状态。** 节点只返回改动的字段，框架把它合并进整体状态，再传给下一个节点。
3. **一个兜底的步数上限。** 图转得太久会抛 `GraphRecursionError`。

框架还提供断点续跑、流式输出、中途等人确认、并行分支。这个任务没有用到，本文没有评估它们。

## 它藏起了什么

这些是把手写版改写成图时，必须自己弄清楚才能写对的地方：

1. **“什么时候停”分散到了三处。** 手写版只有一处：`for` 循环的范围，加一个 `return`。
   图里是两条条件边各判断一次，外加框架自己的 `recursion_limit`。
   实测当前版本的默认上限是 10007 步，对 Agent 来说等于没有上限，自己的步数限制一条都不能少。
2. **状态怎样合并要自己记住。** 默认是整个字段覆盖。想往列表里追加一项，要写成 `state["trace"] + [event]`；
   如果直接改传进来的列表，不会报错，但这不是框架承诺的用法。手写版里就是普通的 `list.append`。
3. **一步被拆成两个函数。** 手写版里“模型输出 → 解析 → 执行工具 → 记录”在同一段代码里，一条 `event` 从头用到尾。
   图里解析在模型节点，执行在工具节点，工具节点要从状态里取回上一条记录、复制、再放回去。87 行里多出来的大部分是这类搬运。
4. **出错时的调用栈。** 手写版的异常直接指向循环里的那一行。图里的异常要穿过框架的调度层。
5. **依赖里带着联网的部件。** 38 个包中有 `langsmith`（追踪服务的客户端）和几个 HTTP 库。
   本项目在 `config.py` 里显式关掉了追踪（`LANGSMITH_TRACING=false`）。没有检查过不关时的默认行为，这里只记录“需要知道它存在”。

## 判断

对这个任务（两个工具、最多几步、单线流程），框架没有带来手写版做不到的东西，多出的是代码量、依赖和几条需要记住的规则。

这个结论只对这么小的任务成立。断点续跑、人工确认、并行分支都没有测，
任务长到需要它们时，结论可能反过来。到那时值得再比一次：先手写，看看自己要补多少代码。

## 对后续工作的含义

- 停止条件值得作为一个独立的研究对象：它在手写版里只有一行，却是两种写法差别最大的地方。
- 先手写再对照框架，这个顺序有效：87 行里的每一处搬运，都对应着手写版里一件“本来就在做、但没意识到”的事。
