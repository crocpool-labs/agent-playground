# 通用性：第二个模型能不能不改引擎跑通

2026-11-27 · 原始记录 `experiments/generality.json` · 重跑 `.venv/bin/python -m tiny_agent.generality` · 测试 `tests/test_generality.py`

## 结论

**不能。** 手写引擎原来只为 Qwen3-0.6B 写，直接换模型会在加载时报错。
改成“一份模型描述 + 一个只看描述的引擎”之后，三个模型走同一条路径，float32 下与 mlx_lm 的 logits 最大相差不到 0.002，
16 道题的贪心生成逐 token 相同。

更有用的是“为什么不能”的清单：它标出了抽象真正该放在哪里。

## 做了什么

| 模型 | 与 Qwen3 的关系 | 原代码直接运行 |
| --- | --- | --- |
| Qwen3-0.6B | 原有模型 | 通过 |
| Qwen2.5-0.5B | 同一家的上一代，结构相近 | `KeyError: 'head_dim'` |
| Gemma-3-270M | 另一家，结构差别大 | `KeyError: 'tie_word_embeddings'` |

三个模型都是 mlx-community 的 4-bit 权重，版本固定在 `tiny_agent/config.py` 的 `MODELS`。

`tiny_agent/transformer.py` 现在分成两半：

- `describe()`：读 `config.json` 和权重名，产出一份纯数据的描述
- `HandModel`：只看这份描述做计算，代码里不出现任何模型名

## 每个模型逼出了哪些改动

**Qwen2.5（3 处，都只是描述层面的）**

| 差异 | 原来的假设 |
| --- | --- |
| `config.json` 不写 `head_dim` | 一定有这个字段。现在缺省时用 `hidden_size / 头数` |
| q、k、v 三个线性层带 bias | 线性层没有 bias |
| 没有 q_norm、k_norm | 每层都有 |

**Gemma-3（6 处，其中 3 处改到了前向计算的结构）**

| 差异 | 性质 |
| --- | --- |
| 每个子层前后各一个 norm（共 4 个），子层输出先归一化再加回残差 | 结构 |
| 18 层里 15 层是滑动窗口注意力，只看最近 512 个 token | 结构 |
| 窗口层与全局层用不同的 RoPE 底数（1e4 与 1e6） | 结构（每层一个参数） |
| 激活函数是 GELU（tanh 近似），不是 SiLU | 参数 |
| 词向量要乘 √hidden；注意力缩放用单独的配置值 | 参数 |
| norm 权重存的是“减 1 之后的值” | 参数 |

**不在模型里、却同样会让结果出错的 3 处**

这三处都在分词和对话模板一侧，只用 Qwen 时完全看不出来：

1. **重复的 `<bos>`。** Gemma 的对话模板自己写了 `<bos>`，分词器默认又加一个。不报错，但输出明显变差。
2. **结束 token 不止一个。** Gemma 的分词器只登记了 `<eos>`，对话实际以 `<end_of_turn>` 结束，后者写在 `config.json` 里。漏掉它，生成停不下来。
3. **没有 system 角色。** Gemma 的模板把 system 消息并进第一条 user 消息。模板自己处理了，但这说明“消息列表”不是一个与模型无关的接口。

## 哪些东西一行都没改

- **生成循环和 KV cache**（`handgen.py`）。滑动窗口是在注意力的遮挡里实现的，缓存照旧保存全部历史。
  这样结果正确（测试覆盖了超过 512 个 token 的情况），但没有省下内存；要省内存，缓存也得知道窗口大小。
- **采样**（`sampling.py`）。
- **4-bit 反量化、RMSNorm、RoPE、注意力这几个基础函数**。

## 抽象该放在哪里

描述里一共 17 个字段。按这次的经验分三类：

- **标量参数**（层数、头数、eps、底数…）：`config.json` 基本可信，照读即可。
- **“有没有”一类的结构开关**（bias、q/k norm、4 个 norm、输出层是否共享）：`config.json` 不可靠。
  Qwen2.5 的配置里没有 bias 字段，Gemma 的配置里没有“是否共享词表”字段。这些现在直接看权重文件里有没有对应的名字。
- **每层不同的属性**（窗口、RoPE 底数）：描述必须是“每层一份”，不能是“全模型一份”。

对 `infra-models` 与 `infra-infer` 的含义：

1. “描述模型”和“运行模型”可以分开，分界线就是这份描述。
2. 描述要从**权重**核实，不能只转述配置文件。
3. 对话模板、`<bos>` 规则、结束 token 集合属于“模型是什么”，应当放在描述一侧，不应留给调用者各自处理。

## 一个没想到的发现：低精度下，库自己都不稳定

权重文件的原始精度是 bf16 或 fp16。把库和手写引擎各自在原始精度与 float32 下运行，比较 16 道题的贪心生成（最多 40 个 token）：

| 生成结果逐 token 相同的题数（共 16） | Qwen3 | Qwen2.5 | Gemma-3 |
| --- | ---: | ---: | ---: |
| 手写 float32 与 库 float32 | 16 | 16 | 16 |
| 手写 原始精度 与 库 原始精度 | 15 | 16 | 7 |
| 库 原始精度 与 库 float32 | 14 | 16 | 6 |

| logits 最大绝对差 | Qwen3 | Qwen2.5 | Gemma-3 |
| --- | ---: | ---: | ---: |
| 手写 float32 与 库 float32 | 0.0002 | 0.0015 | 0.0008 |
| 库 原始精度 与 库 float32 | 1.50 | 0.31 | 8.57 |
| （logits 的量级） | 38 | 36 | 81 |

读法：

- 第一行说明**实现没有错**：float32 下三个模型都与库一致。
- Gemma-3 在 bf16 下，**库与它自己的 float32 版本**只有 6/16 的生成相同。差异不来自手写实现，来自精度。
- 所以“输出与参考实现一致”这个标准要加一句：**在什么精度下**。Gemma 的参考应当取 float32。

这也修正了旧 README 的一个说法。之前把手写版与库的差距（Qwen3 上约 0.9）归因于 RoPE 和注意力的舍入顺序；
实测主要来源是低精度本身，换成 float32 后差距降到 0.0002。

## 速度（粗略）

手写引擎每个 token 约 9–17 毫秒，库约 3–13 毫秒。只跑了一遍，库的数字包含处理提示词的时间，机器上同时有别的任务，只能看量级。

## 没有做的

- 只验证了 4-bit、输入输出共享词表的模型。
- 三个模型都是同一类解码器。差别更大的结构（例如带状态空间层的）没有试。
- LoRA 适配器只在 Qwen3 上验证。
- 没有做批处理，也没有做性能优化。
